How Trunk Recorder Pro is built

A guide for developers: how samples get from an SDR to a call file, how each signal is decoded, how calls get recorders, why one slow part never stalls the rest, how plugins attach, and what the data and the config look like. Click any box in a diagram for detail. Every diagram is also written out as text beneath it.

01Cargo.toml · crates/*

The big picture

The work is split so that the hard parts (signal processing, decoding, trunking, deciding what to save) never touch a device, a thread, a file or a socket. trunk-core and trunk-app take samples and a wall-clock time and return values: events, JSON strings, WAV bytes. The platform crates own everything with side effects. This is why the same recording logic runs in the desktop program and inside a browser Web Worker, and records bit-identical calls from the same capture.

The browser build has no threads. engine.worker.ts pulls blocks from WebRtl::next() (WebUSB), calls WebSession.push and poll on a timer, and keeps call files in OPFS. It speaks the same messages as the desktop WebSocket, so the interface code is shared.

The recorder's lifecycle

Ctx.lifecycle (runtime.rs) is one Mutex<Lifecycle>: Idle, Recording(Runner), Surveying(SurveyRunner) or Quitting. Only Ctx's methods change it, each holding the lock throughout (begin_recording, begin_survey, with_radios for profiling a source, stop_recording, stop_survey, quit), so two starts never interleave and nothing starts once quitting. The phase the browsers see (state: idle, starting, running, stopping) is the engine thread's report.

While recording, everything for the engine thread goes through one channel, Ctx.engine (Ctx::tell_engine): EngineCmd::Source (a source's error or end, by way of its decoding thread), Topics (what the browsers watch), Talkgroups (a talkgroup file changed) and Keys (a key container unlocked or locked). The plugin host is cloned once per loop (Plugins::host()), so a plugin reload never waits on the engine.

From SDR to saved call

Samples cross a thread boundary twice: from the radio's thread into the source's decoding thread, and from the engine's events out to the engine thread. Between those two points everything happens synchronously on the source's decoding thread (dsp-N), in a fixed order, one channelizer block at a time: its channels are decoded under the source's own lock (each control channel under a lock of its own), then followed under the engine's, so sources decode on cores of their own while the calls are followed in one place. Locks are never nested except the engine's with one other. Press Follow a block to walk the path, or click any stage.

Latency, roughly: the driver's block (RTL about 55 ms, others about 10 ms) + up to one channelizer block (5.12 ms at 2.4 MSPS) + filter delay (under 1 ms) + any backlog in the source queue + decoder framing (the C4FM receiver's block timing adds about 100 ms).

03trunk-core/src/dsp/channelizer.rs

The channelizer

Each source has one channelizer: an overlap-save fast-convolution filter bank, modelled on CyberEther's multi-head filter_engine. One forward FFT per block is shared by every channel the engine listens to. A channel is a head: an M-bin slice of that spectrum multiplied by the channel filter, an M-point inverse FFT (which is also the decimation), and a phase rotation. Opening one more channel costs one small inverse FFT, not another full-rate filter.

Step per blockWhat happens
Collect12,288 new samples (L = N − P + 1) after the 4,096 carried over from the last block. u8 becomes (b − 127.5)/127.5; an odd trailing byte waits for the next buffer so I and Q never swap.
FFTOne 16,384-point forward FFT, no window (rectangular overlap-save). The spectrum is stored in the pre-roll ring.
Each headM bins around the head's bin × the cached filter response (a 4,097-tap Blackman windowed-sinc at the channel's cutoff) → M-point inverse FFT → keep the valid L/D outputs → overlap-save phase correction (exact, integer mod N) → residual NCO for the part of the offset between bins.
Side outputsThe same spectrum gives the waterfall (power_spectrum), the noise floor per slice (noise_profile: median |X|² / ln 2, in floor_slices(fs) slices: 64, fewer where a slice would be under 30 kHz; floor_slice finds the one under a frequency) and the conventional energy detector (band_power), so an idle conventional channel needs no head at all. From the floor, noise_in_band gives the noise a filter passes and threshold a carrier level so many dB above it: the one threshold the trunked analog squelch and conventional's carrier meter both use.

Pre-roll

The ring keeps max(prerollS, 0.3 s, 0.1 s) of spectra. When a grant opens a voice channel, add_head replays up to prerollS (1 s by default) of stored blocks through the new head, so the call starts with the air before the grant. It also returns the absolute input-sample index of the head's first output, which ties every frame time to the source's sample clock. Replayed and live output are identical.

Every channel is a chain: head → receiver → framer → decoders → vocoder. Receivers turn channel IQ into Symbol { dibit, sample, rel_hi, rel_lo }; the soft reliabilities carry through to soft-decision FEC. Pick a chain, then click a block.

05trunk-core/src/trunk/{control,engine,identity,message,calls}.rs

How trunking messages are processed

Every protocol decodes its control channel into the same struct, trunk::Message. Above that line nothing is protocol-specific: one Trunk per site handles hunting, the site lock, AutoTune and the clock, and one CallManager per site turns messages into calls for P25, SmartNet, DMR and NXDN alike. What a system decides (talkgroups, rules, keys) is its SystemConfig's, kept once for all its sites and handed to the call manager as a Policy. How a site listens is one enum, decided once by Trunk::start from its protocol's CarrierPlan: Listening::Off, Hunting(Hunt) or Watching(Vec<Carrier>). The control channel decodes on its source's decoding thread, under its own lock; the site follows the CcResult under the engine's, without taking that lock. Choose a protocol to see its front end.

Hunting, AutoTune and patches

  • Hunting (CC_HUNT_S = 5 s). If no step decoded cleanly for 5 s and the system lists more than one control channel, tune(next) removes the control head, opens one on the next covered frequency, resets the protocol and forgets the site's identity. Steps from a site that fails the lock never count as good, so a foreign control channel is hunted away from. DMR and NXDN watch every carrier and never hunt.
  • AutoTune. Every 10 s, if the control channel decoded in the last second, the site takes the receiver's offset (CcResult::offset_hz) and records ppm = applied ppm + offset/f × 10⁶, and so does each call of a second or more (|ppm| ≤ 50; the median of the last 20, of both kinds; kept for the next run in tune.json). With autoTune on, new heads open at f × (1 + ppm·10⁻⁶) − centre, and a P25 control channel more than 150 Hz off is reopened (at most every 200 s). The error is always measured and shown.
  • Patches. Supergroup → member → last heard. Members expire after 10 s (P25) or 4 s (SmartNet). A call's patched_talkgroups come from members_of(tg).
06trunk-core/src/trunk/{calls,engine,voice,multisite}.rs

How recorders are managed and assigned

A recorder is not a pre-built object as in Trunk Recorder. It is a Recording (audio, vocoder frames, transmissions, reception meter) in Radio.recordings, plus a channelizer head and a voice decoder that exist only while the call does. Radio is shared by every site: each source's radio side behind its own lock (rx: Arc<Vec<Mutex<SourceRx>>>: its channelizer, its voice channels keyed by (site, frequency), its control channel taps, its copy of each site's VoiceParams), the engine's one copy of the sources' settings (cfgs: Arc<[SourceConfig]>), the recordings, the recorder numbers, the calls followed without a recorder (followed) and the outputs to apply (pending). maxRecorders (32) caps how many recordings exist at once; recorder numbers are reused lowest-free. Try a grant below.

While recording

Decoder outputs (VoiceOut { slot, out: TrackerOut }) are routed to the call on their slot, queued in radio.pending and applied after the block (apply_pending) at the site's control channel clock, so a voice channel never borrows its Trunk mutably. Each output finds its site, recording and call once. Audio is appended to the recording and moves last_audio_s; Info adds the talking unit and latches encrypted/emergency (CallUpdate); Cipher, Decrypted and WrongKey follow the encryption; Position gives Event::UnitPosition; Alias teaches a talker alias. Live audio leaves as Event::Audio from the copy that leads its multi-site conversation.

Ending, splitting and freeing

  • End. CallManager::tick ends a call when the control channel has said nothing about it for callTimeoutS (3 s), and either it isn't recording or its audio has also been quiet that long. RecorderHost::release clears its slot; the head closes when both slots are empty.
  • Split. A call longer than maxCallS (or 600 s when that is 0) is saved and carries on as a new call id on the same channel and recorder (record_continued, which skips the maxRecorders check so it can't lose its recorder).
  • A call per transmission. With conversationMode off (CallConfig::conversation) the same split happens at each new transmission: apply_pending, taking a recorded call's audio after more than TRANSMISSION_GAP_S (0.5 s) of none, or a new talker after the last had talked that long, asks CallManager::next_transmission; the audio (and what's queued after it in that pass) goes to the new call, with the talkers announced since.
  • Free. The recorder is returned in Core::conclude, at the end of the block, when the recording is removed and its number goes back to free_nums.
  • No priority, no preemption. A call refused with no_recorder stays monitored until it times out and is not retried. The talkgroup CSV's Priority only matters when negative (ignore); Message.priority is written to the call JSON and used nowhere else.

Multi-site: every copy is recorded

Sites are twins when they are sites of one system (one SystemConfig's sites); nothing is grouped from what the control channels announce. Calls on twin sites with the same talkgroup (or, unit to unit, the same radio called) that start within 3 s (Span::starts_with) are linked into one conversation (Call::twin marks the later copies), one copy from each site (MultiSite::link), so copies never chain. Unlike Trunk Recorder, every copy gets a recorder. Live audio follows one copy until it has been quiet for 0.5 s. When the last copy ends they're tried best first: the talkgroup's preferred site if its clean voice is at least 90 % of the best, otherwise the most clean voice, then fewest FEC errors, then the earliest start. Each is saved unless one saved holds it (Kept::holds: another site, its whole Span, the same talkers where known, at least as much clean voice give or take 90 %); those become Duplicate events. Every copy saved gets the same transmission_id.

Buffering and back-pressure, compared with GNU Radio

Trunk Recorder is a GNU Radio flowgraph: many blocks, each on its own thread, joined by circular buffers. Trunk Recorder Pro is one thread per source that runs every stage to completion for each block, with one blocking queue in front of each and non-blocking, explicitly lossy queues behind it. Pick a slow part in each diagram to see where the pressure goes.

08trunk-pro/src/plugins/ · crates/trunk-recorder-plugin

Plugins

A plugin is a separate executable that only watches: nothing it does changes what is recorded. It reads JSON lines on stdin (HostMessage), writes JSON lines on stdout (PluginMessage), and anything it prints on stderr becomes a log line. Each runs in its own process group, so Ctrl-C reaches only the recorder, which then shuts the plugins down in order.

Writing one in Rust

The trunk-recorder-plugin crate has CallRecord, the call JSON as one typed record: the recorder makes one per call (record::call_record), writes the .json from it (CallRecord::to_json, byte for byte as the files always were) and hands the same record to the history and the plugins; every field it writes is named, others are kept in extra, flags are written 0/1 and read as 0/1 or booleans. Its sdk feature gives a Plugin trait (typed Config and SystemConfig with schemas from schemars; start, call_concluded, unit, audio, status, shutdown…) and run::<P>() for --describe, the handshake and exit codes. CallQueue adds worker threads (2 per lane: a queue per server), retries at 10 s, 60 s, 300 s and 900 s, endpoint health, metrics and a queue.jsonl that survives restarts. TalkgroupFilter gives allow/deny globs; testing drives a plugin with messages against an HTTP mock server.

10trunk-app/src/config.rs · trunk-pro/src/paths.rs

The configuration file

One JSON file, config.json, written whole by the interface through an atomic write (temporary file, sync, rename). It is versioned: Ctx.config_version goes up by one at every change (Ctx::config_changed, which tells every browser config { config, version }), and setConfig { config, version } names the version it was edited from, so an edit of an older one is refused (configSaved with an error) rather than saved over another browser's change. Keys are camelCase. Unknown keys are kept and written back at the top level and inside each system, conventional system, recording, server and log; a value of the wrong type makes the file unreadable rather than half-read, and so does a closed choice it doesn't list (a system type, modulation, nxdnType, nxdnRate, defaultMode, vocoder, the M4A encoder, unitNames.mode, the log's color, level and formats, an interface's access, a channel mode…): each is declared once by the choice! macro (trunk-app/src/choice.rs) with its names, read in any case ("P25", "QPSK"), "" meaning the default. A source's type is the tag of Source, put in its own case by Config::from_value before it is read. Click any key in the example to see what it means.

Where it lives

  • macOS ~/Library/Application Support/trunk-pro/config.json; Windows %APPDATA%\trunk-pro\; Linux $XDG_CONFIG_HOME/trunk-pro/ or ~/.config/trunk-pro/; Docker /data/config/trunk-pro/; browser localStorage["trp.config"].
  • --config file.json uses another file, and its folder becomes the data folder for every companion file, so two configs in different folders share nothing.
  • Talkgroup files are not in it: each system's (trunked or conventional) is <shortName>.talkgroups.csv beside it (config::talkgroups_path; TalkgroupFiles by short name), written by setTalkgroups and taken by a recording at once (EngineCmd::Talkgroups). The browser keeps them in localStorage["trp.talkgroups"].
  • Every upgrade of an older config is in migrate.rs (migrate::config, run by Config::from_value: key files named by systems, interfaces as a list and server.home, each site a system of its own, talkgroups in the config); what it changed is in Config::notes. The desktop app saves an upgraded one (migrate::save), keeping the old file as config.json.before-sites.
  • Flags for one run only, never saved: --port, --bind, --start (as autoStart), --log-level, --ui, --no-open.

Every key

From config to engine

Config::engine_config(epoch_ms, &TalkgroupFiles) builds trunk-core's EngineConfig, whose systems are kept once for a whole system. Each active system (enabled, with an active site) becomes a SystemConfig: its short name, its CallConfig and SaveRules (global recording overlaid with the system's own), its talkgroup file and unit tags (keys are set by the app), and its active sites, each a SiteConfig (its name, control channels, receiver bank, expect and protocol). Then each active conventional system becomes a SystemConfig with no sites and its own talkgroup file; its enabled channels become channel rows naming their system's number. Sources get their resolved centres. File names, archive rules, M4A, the spool, server, log, monitor and plugins never reach the engine; the platform uses them.

Config::call_systems numbers every system as the engine does: active trunked systems 0, 1, …, then the active conventional systems. It is the one place that number is worked out: the engine, plugins, status (status.systemNames) and the interface all go by it. There is no limit on conventional systems. The per-system recording settings are declared once (the recording! macro's per_system block makes Recording, RecordingOverride and Recording::with), and Config::recordings() resolves every system's once when recording starts.

Checked at Start, first failure wins

  1. No sources.
  2. A file source without a path.
  3. An RTL-SDR's bufLen not a multiple of 512 (or over 16 MiB), or more than 256 buffers.
  4. Nothing to record (no active system and no enabled conventional channel).
  5. A missing or duplicate short name, across trunked and conventional, enabled or not; or two sites of a system with one name (Config::name_problem).
  6. A source whose centre can't be resolved by auto-centring.
  7. An active site's bad SmartNet band plan, DMR / NXDN carriers outside every source, or no control channel inside one.
  8. One frequency in two conventional systems.
  9. A channel frequency ≤ 0, or outside every source.
  10. A tone that doesn't parse for its mode.
  11. An analog channel's bandwidthKhz outside 4–20, or a demod setting out of range.
  12. A file name format with a token nobody knows (the config's, or a system's own).
  13. Rows sharing a frequency that can't be told apart (same mode required; at most one without a code).

The interface runs this same code (section 13), so Setup says what Start will say.

Auto-centring. Sources with centerHz 0 are placed in order over the systems not yet covered: start at the midpoint of the frequencies (rounded to 1 kHz), step to either side in widening 12.5 kHz steps until no channel is within 25 kHz of DC (off_dc), and accept when every frequency is inside half-width − 10 kHz. The first-run guide places sources for a system found on the air with plan_centers, through the same off_dc.

11trunk-app/src/session.rs (ClockFit) · trunk-core/src/trunk/engine.rs

Time, clocks and identifiers

The engine has no wall clock. Every time inside it (a frame, a message, a call's start, a timeout) is a source's sample count divided by its rate, plus that source's clock offset. This makes a capture decode the same at any speed. The offset is the one link to the wall clock. Session keeps it for each live source with ClockFit, which measures each buffer against the instant its driver handed it over.

Watch the offset being steered

Each dot is one buffer's lag: the wall time since start minus the source's sample time. Buffers only ever arrive late (USB, driver buffering), so the lowest lag in each 10 s window is the clock's own. The dashed line is each window's minimum (the target); the solid line is the offset set on the engine.

  • Where each part of the clock's time comes from. Each Trunk (a site) takes its time from its control channel's source, and every voice output of a block is applied at it, whichever source its channel is on; the engine's own now_s comes from source 0. Wall time is the epoch taken at start plus engine time. Session applies the local UTC offset for folder names, which only the platform knows.
  • Gaps. Samples a driver reports dropped (Feeder::gap), and a running source that sends nothing for over a second (Feeder::idle; fill_quiet in the browser), are fed as faint noise (up to 10 s). Calls on a dead source still time out, and sources stay comparable for multi-site matching. Conventional channels don't learn their noise floor from it or open on it.
  • Not live. A capture played as fast as it can be keeps pure sample time; ClockFit ignores it.

The dashboard's measurements

What the dashboard shows is measured by parts kept out of the decoding code. A decoding part keeps plain counters and current values in its own fields: no locks, no allocation, nothing on the sample path beyond an increment. About once a second it is asked to list them (Instrumented::report into a Sink). Rates, history, storage and presentation belong to whoever asks.

PartWhat it does
Sink: counter / gaugeA counter is a running total (it may restart at 0 when a part is replaced, such as a retuned control channel) that the reader turns into a rate; a gauge is a current value. Names are short and /-separated and become series keys such as sys/<shortName>/cc/good, so renaming one loses its history.
AggregatorRates from counters, each series' value now (the stats message every second), and per minute its average, lowest and highest: a Rollup {"t": minute, "s": {key: [avg, min, max]}}.
HistoryA minute grid per series, a week in memory. statsQuery (names or prefixes ending in *, over 10 m to 7 d) is answered downsampled to about the points asked for (360 by default).
stats filesstats/YYYY-MM-DD.jsonl (UTC days): rollups appended, never rewritten; a finished day is gzipped; days past 8 deleted; read back into History in the background at start (statsResult says loading meanwhile).
RegistryPer system, bounded maps of talkgroups (5,000), units (20,000), unit pairs, frequencies and affiliations, with hourly activity for a week. Answers radioQuery; saved as radio/<short>.json every 15 min and at stop.
NameBookEach system's talkgroups (as engine_config makes them) and talker aliases, by short name: the names radioQuery answers with. The session keeps it current; the desktop app fills it at start, on config changes and talkgroup edits.
MonitorNotable events: talkgroup or unit first seen, talkgroup active, call volume, control channel lost / regained (MonitorEvent::ControlLost { system, site, … }: the system's short name and the site's own name), source drops, clipping, disk and spool space. Each goes to the registered watchers (the hook for alert rules; none yet) and, if it is one for the feed, to browsers as monitorEvent. The last 200 are sent when a connection is greeted.
monitor thread (desktop)Every 2 s the computer (CPU, memory, disks, cgroup limits, container detection; internet checks every 15 s) and the plugins (queued, retries, latency, drops) report into their own aggregator: a host message to browsers, and rollups into the same history.
Per-channel detailVoiceDecoder::quality() and ControlChannel::quality() (ChannelQuality) reach Engine::channels(), sent only to clients subscribed to rf:<source> (rfDetail) or decode:<shortName> (decodeDetail).

A new protocol brings its own figures through ControlChannel::report (default: nothing); Engine::report adds what every system and source shares (levels, ppm, calls). The registry, the name book and the monitor live in stats::Shared, which the platform holds so they outlive a recording session.

The config rules in the interface

The interface doesn't write the config's rules again: it runs the recorder's own, compiled to WebAssembly, in both builds (the desktop app's page too). crates/trunk-web/src/rules.rs exports, over trunk-app's config.rs: configNormalize (a config as the recorder reads it, an older one upgraded, with its notes), configTalkgroups (the talkgroup files an older config held), configProblem (Config::problem), configNameProblem, configCenters (resolved_centers), autoCenter, planCenters, usableHalfWidth, channelsParse / channelsWrite (the channel CSV) and bandplanProblem. web/src/rules.ts loads them before the page renders (loadRules) and keeps each answer for the store's config until it is replaced (configReplaced). So the dashboard needs a browser with WebAssembly SIMD (Safari 16.4, Chrome 91, Firefox 89 or later), and says so if it hasn't. Left in TypeScript on purpose: the file name chip editor, the tone and talkgroup parsers used for inline hints, and the builders for new cards and the Trunk Recorder import.

14web/src/protocol.ts · trunk-pro/src/server.rs · docs/api/

The interface protocol

Everything the interface does goes over one WebSocket, /api/ws: JSON text both ways, plus binary frames for live audio. web/src/protocol.ts is the source of truth; docs/api/protocol.schema.json is generated from it (npm run schema). The Rust side is two enums in trunk-app/src/protocol.rs: ToClient (every message, serialized as {"type": <variant>, …}, with audience()) and Command (every command, read strictly by Command::parse, with listen_may_send()); trunk-pro/src/protocol_tests.rs checks their variants against protocol.ts both ways and the messages against the schema. Every message to the browsers goes through runtime::publish, which serializes it once as each kind of connection may hear it (Out::of: for everyone, control access only, or the config in two versions, the listen one without plugin settings and key sources); bodies still put together as JSON ride as a Body. A command that doesn't parse, or that the connection's access doesn't allow, is answered with an error. hello.capabilities (service, drivers, plugins, interfaces, host, keys) says what a recorder can do beyond recording, so an interface shows what works rather than checking which build it is. The full reference for people building their own interface is docs/api/README.md.

These are served on the built-in interface's port and, the same, on each other interface's (server.interfaces, a listener each, kept by interfaces::serve::reconcile as the config changes). The port a request came in on decides what a WebSocket may do (access.rs): control on the built-in port; on an interface's, its access: listen may only subscribe, query, page through calls and listen, gets no plugin, interface or key messages, and sees the config without plugin settings and key sources.

Every request passes a guard. Programs that aren't browsers send no Origin and are let in. A browser page must be the recorder's own origin or listed in server.allowedOrigins (which also gets CORS headers); anything else gets 403. Bound to localhost, the Host must be localhost too, so a site whose name was pointed at 127.0.0.1 (DNS rebinding) is still another site. A client that falls more than 4,096 messages behind on the hub skips the oldest without notice.
