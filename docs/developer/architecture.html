How Trunk Recorder Pro is built

A guide for developers: how samples get from an SDR to a call file, how each signal is decoded, how calls get recorders, why one slow part never stalls the rest, how plugins attach, and what the data and the config look like. Click any box in a diagram for detail. Every diagram is also written out as text beneath it.

01Cargo.toml · crates/*

The big picture

The work is split so that the hard parts (signal processing, decoding, trunking, deciding what to save) never touch a device, a thread, a file or a socket. trunk-core and trunk-app take samples and a wall-clock time and return values: events, JSON strings, WAV bytes. The platform crates own everything with side effects. This is why the same recording logic runs in the desktop program and inside a browser Web Worker, and records bit-identical calls from the same capture.

The browser build has no threads. engine.worker.ts pulls blocks from WebRtl::next() (WebUSB), calls WebSession.push and poll on a timer, and keeps call files in OPFS. It speaks the same messages as the desktop WebSocket, so the interface code is shared.

02trunk-pro/src/runtime.rs · trunk-app/src/session.rs · trunk-core/src/trunk/engine.rs

From SDR to saved call

Samples cross a thread boundary twice: once into the engine, once out of it. Between those two points everything happens synchronously on the engine thread, in a fixed order, one channelizer block at a time. Press Follow a block to walk the path, or click any stage.

Latency, roughly: the driver's block (RTL about 55 ms, others about 10 ms) + up to one channelizer block (5.12 ms at 2.4 MSPS) + filter delay (under 1 ms) + any backlog in the source queue + decoder framing (the C4FM receiver's block timing adds about 100 ms).

03trunk-core/src/dsp/channelizer.rs

The channelizer

Each source has one channelizer: an overlap-save fast-convolution filter bank, modelled on CyberEther's multi-head filter_engine. One forward FFT per block is shared by every channel the engine listens to. A channel is a head: an M-bin slice of that spectrum multiplied by the channel filter, an M-point inverse FFT (which is also the decimation), and a phase rotation. Opening one more channel costs one small inverse FFT, not another full-rate filter.

Step per blockWhat happens
Collect12,288 new samples (L = N − P + 1) after the 4,096 carried over from the last block. u8 becomes (b − 127.5)/127.5; an odd trailing byte waits for the next buffer so I and Q never swap.
FFTOne 16,384-point forward FFT, no window (rectangular overlap-save). The spectrum is stored in the pre-roll ring.
Each headM bins around the head's bin × the cached filter response (a 4,097-tap Blackman windowed-sinc at the channel's cutoff) → M-point inverse FFT → keep the valid L/D outputs → overlap-save phase correction (exact, integer mod N) → residual NCO for the part of the offset between bins.
Side outputsThe same spectrum gives the waterfall (power_spectrum), the noise floor per slice (noise_profile: median |X|² / ln 2) and the conventional energy detector (band_power), so an idle conventional channel needs no head at all.

Pre-roll

The ring keeps max(prerollS, 0.3 s, 0.1 s) of spectra. When a grant opens a voice channel, add_head replays up to prerollS (1 s by default) of stored blocks through the new head, so the call starts with the air before the grant. It also returns the absolute input-sample index of the head's first output, which ties every frame time to the source's sample clock. Replayed and live output are identical.

DSP chains

Every channel is a chain: head → receiver → framer → decoders → vocoder. Receivers turn channel IQ into Symbol { dibit, sample, rel_hi, rel_lo }; the soft reliabilities carry through to soft-decision FEC. Pick a chain, then click a block.

05trunk-core/src/trunk/{control,engine,identity,message,calls}.rs

How trunking messages are processed

Every protocol decodes its control channel into the same struct, trunk::Message. Above that line nothing is protocol-specific: one Trunk per system handles hunting, the site lock, AutoTune and the clock, and one CallManager turns messages into calls for P25, SmartNet, DMR and NXDN alike. Choose a protocol to see its front end.

Hunting, AutoTune and patches

  • Hunting (CC_HUNT_S = 5 s). If no step decoded cleanly for 5 s and the system lists more than one control channel, tune(next) removes the control head, opens one on the next covered frequency, resets the protocol and forgets the site's identity. Steps from a site that fails the lock never count as good, so a foreign control channel is hunted away from. DMR and NXDN watch every carrier and never hunt.
  • AutoTune. Every 10 s, if the control channel decoded in the last second, the engine records ppm = applied ppm + offset/f × 10⁶ (|ppm| ≤ 50; last 20 averaged). With autoTune on, new heads open at f × (1 + ppm·10⁻⁶) − centre, and a P25 control channel more than 150 Hz off is reopened (at most every 200 s). The error is always measured and shown.
  • Patches. Supergroup → member → last heard. Members expire after 10 s (P25) or 4 s (SmartNet). A call's patched_talkgroups come from members_of(tg).
06trunk-core/src/trunk/{calls,engine,voice,multisite}.rs

How recorders are managed and assigned

A recorder is not a pre-built object as in Trunk Recorder. It is a Recording (audio, vocoder frames, transmissions, reception meter) in Radio.recordings, plus a channelizer head and a voice decoder that exist only while the call does. maxRecorders (32) caps how many recordings exist at once; recorder numbers are reused lowest-free. Try a grant below.

While recording

Decoder outputs (VoiceOut { slot, t, out: TrackerOut }) are queued in radio.pending and applied after the block (apply_pending), so a voice channel never borrows its Trunk mutably. Audio is appended to the recording and moves last_audio_s; Info adds the talking unit and latches encrypted/emergency (CallUpdate); Alias teaches a talker alias. Live audio leaves as Event::Audio from the copy that leads its multi-site conversation.

Ending, splitting and freeing

  • End. CallManager::tick ends a call when the control channel has said nothing about it for callTimeoutS (3 s), and either it isn't recording or its audio has also been quiet that long. RecorderHost::release clears its slot; the head closes when both slots are empty.
  • Split. A call longer than maxCallS (or 600 s when that is 0) is saved and carries on as a new call id on the same channel and recorder (record_continued, which skips the maxRecorders check so it can't lose its recorder).
  • Free. The recorder is returned in Engine::conclude, at the end of the block, when the recording is removed and its number goes back to free_nums.
  • No priority, no preemption. A call refused with no_recorder stays monitored until it times out and is not retried. The talkgroup CSV's Priority only matters when negative (ignore); Message.priority is written to the call JSON and used nowhere else.

Multi-site: every copy is recorded

Sites are twins when they share a site group but are not the same site or control channel. Calls on twin sites with the same talkgroup that start within 3 s are linked into one conversation. Unlike Trunk Recorder, every copy gets a recorder. Live audio follows one copy until it has been quiet for 0.5 s. When the last copy ends one is kept: the talkgroup's preferred site if its clean voice is at least 90 % of the best, otherwise the most clean voice, then fewest FEC errors, then the earliest start. The rest become Duplicate events.

Buffering and back-pressure, compared with GNU Radio

Trunk Recorder is a GNU Radio flowgraph: many blocks, each on its own thread, joined by circular buffers. Trunk Recorder Pro is one thread that runs every stage to completion for each block, with one blocking queue in front of it and non-blocking, explicitly lossy queues behind it. Pick a slow part in each diagram to see where the pressure goes.

08trunk-pro/src/plugins/ · crates/trunk-recorder-plugin

Plugins

A plugin is a separate executable that only watches: nothing it does changes what is recorded. It reads JSON lines on stdin (HostMessage), writes JSON lines on stdout (PluginMessage), and anything it prints on stderr becomes a log line. Each runs in its own process group, so Ctrl-C reaches only the recorder, which then shuts the plugins down in order.

The configuration file

One JSON file, config.json, written whole by the interface (setConfig) through an atomic write (temporary file, sync, rename). Keys are camelCase. Unknown keys are kept and written back at the top level and inside each system, conventional system, recording, server and log; a value of the wrong type makes the file unreadable rather than half-read. Every key

From config to engine

Config::engine_config builds trunk-core's EngineConfig. Active systems (enabled, with a control channel) become SystemConfigs with their CallConfig and SaveRules (global recording overlaid with the system's own), talkgroups, unit tags, receiver bank, expect, protocol and site group. Every conventional entry becomes a ConvSystem so indexes line up; enabled channels become channel rows. Sources get their resolved centres. File names, archive rules, M4A, the spool, server, log, monitor and plugins never reach the engine; the platform uses them.

Checked at Start, first failure wins

  1. No sources.
  2. A file source without a path.
  3. Nothing to record (no active system and no enabled conventional channel).
  4. A missing or duplicate short name, across trunked and conventional, enabled or not.
  5. A source whose centre can't be resolved by auto-centring.
  6. An active system's control channels (and DMR / NXDN carriers) outside every source; a bad SmartNet band plan.
  7. More than 256 conventional systems.
  8. One frequency in two conventional systems.
  9. A channel frequency ≤ 0 or outside every source.
  10. A tone that doesn't parse for its mode.
  11. Rows sharing a frequency that can't be told apart (same mode required; at most one without a code).

Auto-centring. Sources with centerHz 0 are placed in order over the systems not yet covered: start at the midpoint of the frequencies (rounded to 1 kHz), step ±12.5 kHz until no channel is within 25 kHz of DC, and accept when every frequency is inside half-width − 10 kHz.

11trunk-app/src/session.rs (ClockFit) · trunk-core/src/trunk/engine.rs

Time, clocks and identifiers

The engine has no wall clock. Every time inside it (a frame, a message, a call's start, a timeout) is a source's sample count divided by its rate, plus that source's clock offset. This makes a capture decode the same at any speed. The offset is the one link to the wall clock. Session keeps it for each live source with ClockFit, which measures each buffer against the instant its driver handed it over.

Watch the offset being steered

Each dot is one buffer's lag: the wall time since start minus the source's sample time. Buffers only ever arrive late (USB, driver buffering), so the lowest lag in each 10 s window is the clock's own. The dashed line is each window's minimum (the target); the solid line is the offset set on the engine.

  • Where each part of the clock's time comes from. Each Trunk takes its time from its control channel's source; the engine's own now_s comes from source 0. Wall time is the epoch taken at start plus engine time. Session applies the local UTC offset for folder names, which only the platform knows.
  • Gaps. Samples a driver reports dropped, and a running source that sends nothing for over a second, are fed as faint noise (up to 10 s). Calls on a dead source still time out, and sources stay comparable for multi-site matching. Conventional channels don't learn their noise floor from it or open on it.
  • Not live. A capture played as fast as it can be keeps pure sample time; ClockFit ignores it.

The dashboard's measurements

What the dashboard shows is measured by parts kept out of the decoding code. A decoding part keeps plain counters and current values in its own fields: no locks, no allocation, nothing on the sample path beyond an increment. About once a second it is asked to list them (Instrumented::report into a Sink). Rates, history, storage and presentation belong to whoever asks.

13crates/trunk-web · web/src/web/

The browser build

The same Session and Engine, compiled to WebAssembly (wasm32-unknown-unknown with simd128, bound with wasm-bindgen), run in a Web Worker. The RTL-SDR driver is the same pure-Rust rtlsdr-nusb, on nusb's WebUSB backend. The worker speaks the same FromRecorder / ToRecorder messages as the desktop WebSocket, so the interface code doesn't know which one it is talking to.

Every request passes a guard. Programs that aren't browsers send no Origin and are let in. A browser page must be the recorder's own origin or listed in server.allowedOrigins (which also gets CORS headers); anything else gets 403. Bound to localhost, the Host must be localhost too, so a site whose name was pointed at 127.0.0.1 (DNS rebinding) is still another site. A client that falls more than 4,096 messages behind on the hub skips the oldest without notice.
